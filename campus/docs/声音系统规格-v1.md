# 声音系统规格 v1

> 末日生存(校园)· 第一人称 3D · Unity
> 本文档是声音系统的唯一事实来源。所有涉及"听见/听不见"的逻辑,一律以本文档为准。

---

## 0. 系统定位

声音系统是本作的**核心规则层**。潜行、丧尸 AI、昼夜、投掷物、静步与听声熟练度,全部建立在它之上。

它必须在其他系统之前实现,并且**不依赖任何上层系统**。它只知道:

- 有一张地图连通图(由地图数据提供)
- 有一个游戏时钟(由时间系统提供,只读)
- 有一个数值修正管线(用于查询熟练度修正后的最终值)

它**不知道**丧尸、玩家、背包、UI 的存在。所有听者通过统一的 `HearingComponent` 接入。

---

## 1. 设计目标

1. **精确可预测**:同样的动作在同样的位置,永远产生同样的传播结果。没有随机衰减。
2. **符合直觉**:声音绕着开着的门传出去,而不是穿墙走直线。关上门就真的能挡住声音。
3. **玩家可推理**:玩家应该能在脑内建立"我这么做,多远的东西会听见"的模型,并据此做计划。
4. **性能可控**:单次声音事件的传播计算控制在 1ms 以内,支持每秒数十次事件。

---

## 2. 核心数据结构

### 2.1 声音事件 `SoundEvent`

一次声音的全部信息。发出后即不可变。

| 字段 | 类型 | 说明 |
|---|---|---|
| `worldPosition` | Vector3 | 声源世界坐标 |
| `nodeId` | int | 声源所在节点(由坐标查询得到) |
| `loudness` | float | 源响度,0–150,见第 6 节响度表 |
| `category` | enum | `Footstep` / `Impact` / `Voice` / `Gunshot` / `Ambient` / `Door` |
| `emitterId` | int | 发声者实体 ID,-1 表示无主(如落石) |
| `timestamp` | float | 游戏内时间戳 |

`category` 不影响传播,只影响听者的解读(例如玩家 UI 上枪声和脚步显示不同的图标;丧尸对 `Voice` 类的优先级更高)。

### 2.2 房间节点 `SoundNode`

地图被切分成的一块声学空间。一个教室、一段走廊、一个楼梯间、一片室外区域,各是一个节点。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | 全局唯一 |
| `bounds` | Bounds | 空间范围,用于坐标→节点查询 |
| `isOutdoor` | bool | 室外节点,传播规则略有不同(见 4.3) |
| `buildingId` | int | 所属楼栋,用于分区加载 |
| `portals` | List\<int\> | 连接到本节点的所有 Portal ID |

### 2.3 连接 `SoundPortal`

两个节点之间的声学通道。门、窗、楼梯口、破洞、通风管。

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | int | 全局唯一 |
| `nodeA` / `nodeB` | int | 连接的两个节点 |
| `position` | Vector3 | 通道中心点,用于计算路径长度 |
| `type` | enum | 见 6.2 连接类型表 |
| `state` | enum | `Open` / `Closed` / `Broken` / `Blocked` |
| `attenuation` | float | 当前状态下的衰减值,由 `type` + `state` 查表得到 |

**关键:** `state` 是运行时可变的。玩家关门 → `state` 变 `Closed` → `attenuation` 从 5 变 45。这是玩家控制声音传播的主要手段,也是整个潜行玩法的核心交互之一。

Portal 状态变化时,必须发出一个 `PortalStateChanged` 事件,让缓存失效。

### 2.4 听觉组件 `HearingComponent`

**丧尸和玩家共用同一个组件。** 这是本系统最重要的架构决策——避免两套并行的听觉逻辑产生不一致。

| 字段 | 类型 | 说明 |
|---|---|---|
| `threshold` | float | 感知阈值。低于此值的到达响度完全无感 |
| `localizationSkill` | float | 定位精度系数,0–1,越高误差越小 |
| `selfEmitterId` | int | 自己的实体 ID,用于过滤自己发出的声音 |

阈值与精度都**不直接写死**,而是每次使用前向数值修正管线查询最终值:

```
finalThreshold = ModifierPipeline.Query("hearing.threshold", baseThreshold, ownerId);
```

这样听声熟练度、屏息状态、耳鸣负面状态、装备(耳机?)都能统一插入。

## 3. 传播算法

### 3.1 核心公式

```
到达响度 = 源响度
         − 距离衰减系数 × 路径长度
         − Σ(路径上所有 Portal 的 attenuation)
```

其中**路径长度**是声音实际绕行的距离,不是直线距离。

**距离衰减系数** `k`:
- 室内基准 `k = 2.0`(每米衰减 2 点响度)
- 室外基准 `k = 1.2`(开阔地衰减更慢)
- 夜晚全局乘以 `0.7`(声音传得更远,约 +43% 有效距离)

夜晚系数从时间系统读取,建议做成一条随时间平滑变化的曲线而非硬切换,避免 19:00 整点声音突然变远。

### 3.2 图搜索

在 Portal 图上跑一次 **Dijkstra**,代价 = 累计衰减量(距离衰减 + Portal 衰减)。

```
输入: SoundEvent
输出: Dictionary<nodeId, (arrivalLoudnessAtEntry, pathLengthToEntry, entryPortalPos)>

1. 起始节点的入口点 = 声源位置本身,累计衰减 = 0
2. 优先队列按累计衰减升序展开
3. 从节点 N 经 Portal P 到节点 M:
     段长 = distance(N的入口点, P.position)
     新累计衰减 = 当前累计衰减 + k × 段长 + P.attenuation
4. 剪枝: 若 源响度 − 新累计衰减 < GLOBAL_MIN_THRESHOLD,不再展开
5. 每个节点只保留衰减最小的那条路径(自动实现"多通道取最优路径")
```

`GLOBAL_MIN_THRESHOLD` 取全场景所有听者阈值的最小值(通常是屏息状态的玩家,约 8)。低于它的传播没有任何意义,直接剪掉。这个剪枝是性能的关键。

### 3.3 听者结算

图搜索给出的是"声音传到各节点入口时的响度"。听者的最终响度还要加上**节点内的最后一段距离**:

```
若 听者节点 == 声源节点:
    到达响度 = 源响度 − k × distance(声源, 听者)
否则:
    段长 = distance(该节点入口Portal位置, 听者位置)
    到达响度 = 该节点入口响度 − k × 段长
```

这一步解决了纯图模型的最大缺陷:**同一房间内贴脸和隔十米不再等价**。

### 3.4 结算时机

声音事件不是每帧发生的,不要放在 Update 里轮询。

- 事件发出 → 立即跑一次传播 → 结果推送给受影响节点内的所有听者
- 听者是被动接收方,不主动查询
- 同一帧内的多个声音事件可以合并批处理

## 4. 边界情况

### 4.1 未加载区域

分区加载时,**Portal 图始终全量常驻内存**——它只是几百个节点和连接的纯数据,几十 KB,不含任何美术资源。

因此声音传播计算**不受加载状态影响**。未加载楼栋里的简化丧尸依然能正确接收到声音,并更新自己的"大致目标位置"。玩家进入时还原成实体,位置是合理的。

### 4.2 声源与听者不在同一栋楼

正常走图即可。楼与楼之间通过室外节点相连,大门/破窗作为 Portal。枪声能传遍半个校园是**正确行为**,不需要特殊处理。

### 4.3 室外传播

室外没有天然的房间边界。处理方式:

- 把室外按功能区切成若干大节点(操场、主校道、后院、车棚……),相邻室外节点之间用 `type = OpenAir` 的 Portal 连接,`attenuation = 0`
- 室外节点内部,若声源与听者之间有建筑体阻挡,额外扣一次固定遮挡值(建议 25)。这一次判定用射线检测,只针对室外、只在同节点内,数量极少,开销可忽略

### 4.4 移动声源

脚步声是连续产生的离散事件,每一步发一次,不需要连续传播。跑步时约每 0.35 秒一次,走路约每 0.7 秒一次。

### 4.5 自己的声音

`HearingComponent` 过滤掉 `emitterId == selfEmitterId` 的事件。玩家自己的脚步不进入声纹显示,但**仍然会被丧尸听见**——这一点必须保证,否则潜行就没有意义了。

## 5. 听者反应

### 5.1 余量

```
margin = 到达响度 − finalThreshold
```

`margin ≤ 0`:完全无感,直接丢弃事件。

### 5.2 丧尸反应

余量决定反应速度和定位精度,连续变化,不分档:

```
反应延迟(秒)   = clamp(3.0 − margin × 0.06, 0.1, 3.0)
定位误差半径(米) = clamp(12.0 − margin × 0.25, 0.0, 12.0)
```

- 延迟期间丧尸的表现:先停下、转头朝向大致方向,延迟结束后才开始移动
- 目标点 = 真实声源位置 + 在误差半径内的一个随机偏移(**该偏移在事件接收时确定一次并固定**,不要每帧重算,否则丧尸会抖)
- 到达目标点后进入搜索状态,原地徘徊数秒后返回原行为

这套公式自然产生了你要的效果:近处的丧尸几乎立刻扑向准确位置,远处的迟疑几秒后走向一个模糊的方位。**不需要为"远近"写特例。**

### 5.3 优先级覆盖

若丧尸已在追逐某个声音,新事件的 `margin` 必须显著更高(建议 +8 以上)才会切换目标。否则玩家连续投石会让丧尸在原地反复抽搐。

### 5.4 玩家听觉与声纹

玩家的 `HearingComponent` 用同一套接收逻辑,只是把结果送给 UI 而不是 AI。

- **常态阈值**:25。只能听到近处明显的声音。
- **屏息**:阈值降至 8,`localizationSkill` 提升。持续消耗体力,松开即恢复。屏息期间玩家移动速度大幅下降或完全禁止(待定,见第 8 节)。
- **声纹表现**:对每个 `margin > 0` 的事件,在 UI 上显示一个方向指示。
  - 方向角误差 = `(1 − localizationSkill) × 基准角误差`,基准建议 60°
  - 距离感知:只给模糊分级(很近 / 中等 / 很远),由 `margin` 决定,不给精确米数
  - 高熟练度时误差趋近于 0,玩家几乎能锁定确切方位

**注意:** 玩家听到的方向应基于**声音传来的路径入口方向**,而不是声源的真实方向。隔壁房间的声音从门口传来,玩家就该感觉声音来自门口。这才是真实的听感,并且它是免费的——Dijkstra 的结果里已经包含了入口 Portal 的位置。

## 7. 对外接口

### 7.1 发出声音

任何系统只需要一行:

```csharp
SoundSystem.Emit(new SoundEvent {
    worldPosition = transform.position,
    loudness = ModifierPipeline.Query("sound.footstep", 20f, ownerId),
    category = SoundCategory.Footstep,
    emitterId = ownerId
});
```

调用方**不需要知道**图、节点、Portal 的任何事情。

### 7.2 需要从修正管线查询的键

| 键 | 使用方 | 影响 |
|---|---|---|
| `sound.footstep` / `sound.crouch` / `sound.run` | 玩家移动 | 静步熟练度 |
| `sound.loot` | 搜刮 | 手法熟练度 |
| `hearing.threshold` | 听觉组件 | 听声熟练度、屏息 |
| `hearing.localization` | 听觉组件 | 听声熟练度 |
| `hold_breath.stamina_cost` | 屏息 | 体力熟练度 |

### 7.3 依赖

- `TimeSystem.GetNightFactor()` → 返回 0.7~1.0 的当前夜间衰减乘数
- `MapGraph` → 提供 `GetNodeAt(Vector3)`、节点与 Portal 数据
- `ModifierPipeline.Query(key, baseValue, ownerId)`

## 8. 待定问题

以下几点需要在实现前确认,不影响架构但影响手感:

1. **屏息时能否移动?** 完全禁止会让听声变成"停下来读地图",可能打断节奏;允许缓慢移动手感更好但会削弱风险。
2. **声纹是否有冷却或持续时长上限?** 目前只靠体力约束,可能导致玩家全程屏息。
3. **丧尸之间是否会互相传递警戒?** 一只被吸引的丧尸在移动时是否发出声音,进而引来更多——如果会,可能产生雪崩式连锁,需要设上限。
4. **玩家能否听见丧尸的"呼吸/低吼"作为环境声源?** 这会让屏息成为侦查工具而不只是防御工具,建议加,但需要给丧尸设计常态发声频率。

## 9. 性能预算

- Portal 图节点数预估:400–800(整所学校)
- 单次 Dijkstra 在剪枝后实际展开节点数:通常 < 30,枪声等大响度事件 < 150
- 目标:单次传播 < 0.5 ms;峰值每秒 40 次事件
- 图数据常驻,不随场景加载卸载
- Portal 状态变化频率低,可缓存"常态开门"的传播结果作为基线优化(实现阶段再考虑,先做朴素版本)
